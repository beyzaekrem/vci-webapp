# Image Capture
Unlike regular webcams, the computer vision cameras have a two-step process for capturing an image.

* First, the **image needs to be triggert**. This tells the Camera hardware 
    to physically capture an image and place in into its internal buffer. 

* The image data sits there, on the camera hardware, until we request 
    it with Camera.**CaptureNext**

This means:
If you call CaptureNext, and there is no image in the Internal Buffer (because it hasn't been triggered) you will not get an image.
The CaptureNext will wait until there is an image, or throw a BufferTimeout. 

# Image Triggering
The cameras can be set up for different image triggering behavious.

Usually the "main" mode is the cameras triggering themselves with a set frame rate, or as quickly as they can manage (free run). This is the behaviour that most Image capture suits, provided by the manufactureres, will have by default.

Another option is to use a **hardware trigger**. In this setup an external signal is provied to the camera, triggering a single image. (cameras can be configured to trigger more than one image, or to delay a little before actually capturing, etc.)
The hardware trigger lets you *synchronize mutliple cameras*, even when they are distributed across multiple servers. (Unsuripsinly this is the option our setup uses)

The last option is a bit of a hybrid between the two. A **software trigger** triggers a single image, but is generated by this repo rather than a completely separete external source. This is used for local tests, since the vci-capture server does not have access to the hardware-trigger-generator (aka, the trigger_box managed by vci-control).
When software triggering, the function Camera.PerformSoftwareTrigger *must* be called before CaptureNext is called, otherwise there will never be an image in the cameras's internal buffer.
The camera implementation also privides a software AutoTrigger functionality to contiously create software Triggers with a set frame rate.

When in hardware trigger mode, creating a softwaretrigger will have no effect.

# Capture Tasks

gibbs.tasks contains mutliple Capture Tasks tailored to different usecases. 
They all "blindly" call CaptureNext and wait there hoping to get an image. 

* gibbs.tasks.capture CaptureAll - grabs one buffer entry from each camera

* gibbs.tasks.record_capture.RecordCapture - this is a complex task, creating a thread to continously pull images from all cameras and writing them to ssd (aka. dumps)

* gibbs.tasks.ring_buffer RingBuffer - continously grabs images from all cameras, processes and encodes them and saves the encoded images to a ring buffer. Intended for live reconstruction.

* gibbs.tasks.Livestream - very similar to ring_buffer but allows zoom operations on images and uses some default values for processing so it can run on uncalibrated cameras. Intended for livestreams to focus the cameras for initial setup or after a lense change.
